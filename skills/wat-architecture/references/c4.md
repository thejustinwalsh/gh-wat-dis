# C4 in one page

Source: [c4model.com](https://c4model.com) by Simon Brown (CC BY 4.0). Read the site for the full model.

## Abstractions

| Abstraction | Is | Is not |
|---|---|---|
| **Person** | A human who uses the system: a role or persona | A team that builds it |
| **Software system** | The highest level. Delivers value to its users. Usually one team owns it and deploys it together. | A bounded context, a product area, a team |
| **Container** | An application or data store that must run for the system to work: web app, API, worker, CLI, database, bucket, queue | A Docker container, a JAR, a folder, a library |
| **Component** | Related code behind one interface, inside one container. Not deployed on its own. | Every package or folder by default |
| **Code** | Classes, functions, tables | Worth drawing by hand |

A single-page app and its backend are two containers. Files that ship on their own and that another system loads and runs are a container too: a plugin, a set of agent skills, CI workflows. Name the system that runs them in the technology or the description. A folder of source that ships inside something else stays a component. A managed service you control (a bucket, a schema) is a container. A third-party service you call is an external software system.

## Diagrams

| Diagram | Scope | Shows | Reader | Draw it |
|---|---|---|---|---|
| System context | One system | The system, its users, the external systems it talks to | Anyone | Always first |
| Container | One system | Its containers and how they talk | Technical people | For most work |
| Component | One container | Its components | The team that owns it | Only when it helps |
| Code | One component | Classes, tables | — | Never by hand |
| System landscape | An organization | Many systems and people | Anyone | Large orgs |
| Dynamic | One feature or flow | Numbered interactions between elements | Anyone | Sparingly, for a hard flow |
| Deployment | One environment | Nodes, container instances, infrastructure | Technical people, operations | When placement changes |

Context plus container is enough for most teams.

## Notation

1. **Title** states the type and scope: "Container diagram for Storefront".
2. **Key** explains every shape, colour, border and line style in use.
3. **Element** shows name, type, technology (containers and components) and one line on what it does.
4. **Relationship** is one direction, with a label that matches the arrow and says what happens. Container-to-container labels name the protocol.
5. **Acronyms** are explained or avoided.
6. **Colour** never carries meaning alone. Pair it with shape, border or text.
7. The diagram makes sense with no surrounding prose.

## Review checklist

`npx gh-wat-dis diagram` lints for these. Check the rest by eye.

- Does the diagram have a title, and is its type and scope clear?
- Is there a key?
- Does every element have a name, a type and a description? Technology where it applies?
- Does every line have a label, and does the label match the arrow's direction?
- Does every container-to-container line name a protocol or technology?
- Can a new team member read every acronym, colour, shape and line style?

## Common mistakes

| Mistake | Fix |
|---|---|
| Label says "Uses" | Say what moves: "Reads orders from", "Sends receipts through" |
| Message bus drawn as one hub | Draw each topic or queue the change touches, or label the line with the topic |
| Shared library drawn as a container | It is a component inside each container that links it |
| Mixed levels: a class next to a system | Pick one level per diagram |
| 30 boxes | Show the changed elements plus one hop. Split the rest. |
| Arrows both ways | Two lines, or the one direction that matters for this change |
